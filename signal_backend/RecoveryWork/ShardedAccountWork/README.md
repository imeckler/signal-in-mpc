# Incremental account directory checkpoint (candidate)

This replaces no active account or provider. A genuinely new fixture domain is used; the verified predecessor's head3 history is untouched. New schema fixtures may start with fresh identity/session material; reusing old state still requires an authorized migration.

`ShardDirectory.h` is a fixed-depth64 persistent sparse Merkle directory keyed by public opaque conversation slots. Domain-separated canonical nodes encode depth, child digests, and leaf key/generation/ciphertext length/digest/schema/validation provenance. Each replacement writes one leaf and64 immutable branch nodes, never the entire directory. Unchanged subtrees and their recorded validation provenance remain byte-identical. The explicit changed-shard validator is a trusted embedding boundary: it must authenticate the local AEAD shard and consume actual computed private validity; its nonzero pinned program identity is recorded with predecessor root/key/generation/digest/schema. **The current fixtures use public validators, not private validity.** A callback's presence is not an account admission capability.

`ShardCheckpoint.h` checks changed ciphertext availability/digest and strictly successive generations before preparation. Before actual journal voting, it binds the candidate root to the exact phase/slot/context/manifest/party, predecessor certificate/root and Reserve/Commit attempt. Only a certified Commit can restore a root. The narrow alternate local-persistence constructor in `AccountCheckpointCoordinator` uses the existing same-five network, all-party persistence readiness, signatures,4of5 certificates, no-double-sign journal, fresh current-head protocol and complete ancestry; legacy full-layout persistence retains its original adapter. Failed local preparation prevents a vote; unresolved higher Reserve still blocks restart. No private provider or restored capability is created here.
