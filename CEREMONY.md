# The registration ceremony

Written 2026-11-11. Status at the end ("Where this stands").

Until now the account was registered by a conventional client on one machine
(`lss-provision register` locally, `real_signal/register` for the real service), and its secrets
were then dealt to the two computation nodes. One machine saw everything, the password included.

The ceremony replaces that. The two nodes register the account together, in two-party sessions
over the existing in-MPC TLS client. **The account password, and the registration recovery
password, never exist outside the engines**: each node contributes randomness, the values are
formed inside the Boolean engine, they enter the registration request only there, and each node
ends with its XOR share, in the form the existing sessions already take the credentials in.

Scope, by the owner's decision of 2026-11-11 ("it's actually fine if the private keys are in the
clear. it's just the password that needs to be kept secret shared"): the account's **keys are
generated conventionally, in the clear, and both nodes hold them**. There is no joint key
generation and no two-party signing. What that leaves a single node able to do is section 4.

Never run against Signal's service. Everything below was run against the local Signal-Server only.

## 1. What registration produces, and how each value is held

"Both" = in the clear on both nodes. "Shared" = XOR shares, one per node; the value itself only
inside the engines.

| Value | Held | Where | Notes |
|---|---|---|---|
| **Account password** (22 characters) | **shared** | `STATE/ceremony/credentials.share` on each node (bytes 16..38); then the account's row on the database nodes | First 22 characters of base64 of the XOR of 18 private bytes from each node: 132 bits, alphabet `A–Z a–z 0–9 + /` (no `:`, which would end the user name of a Basic credential; the server takes any non-empty password). Made by kernel `ceremony-secrets`. |
| **Basic authorization line** of `POST /v1/registration` (`NUMBER:PASSWORD`, base64) | built in the engines | nowhere | Kernel `ceremony-register-ctr`. Its public beginning (whole base64 groups of `NUMBER:`) is in the frame the controllers build. |
| **Registration recovery password** (32 bytes) | **shared** | `STATE/ceremony/recovery.share` on each node | XOR of 32 private bytes from each node. It can re-register the number without an SMS, so it is treated like the password. It is sent once, inside the registration body, and has no slot in the account's row: the two share files are its only copies. Nothing uses it yet. |
| Later `Authorization` lines (every authenticated socket) | built in the engines | — | Unchanged: kernels `signal-upgrade` / `signal-upgrade-shared` from the stored credentials. |
| ACI identity key pair | both | `keys.json`; the private key also in the account's row (sealed, as before) | Generated by `lss-provision ceremony-keys` on one node. See section 4. |
| PNI identity key pair | both | `keys.json` | Not used by any session. |
| Signed prekeys (ACI, PNI), their signatures | both | `keys.json` | Signed conventionally with the identity keys. |
| Kyber last-resort prekeys (ACI, PNI), their signatures | both | `keys.json` | Decapsulation stays outside the engines (`kem-decapsulate`), as before. |
| One-time prekeys (ten) | both | `keys.json` | Uploaded in the `certificate` stage. |
| Profile key; unidentified-access key | both | `keys.json` | The account accepts sealed sender from anyone (`unrestrictedUnidentifiedAccess`), so the access key protects nothing. |
| Registration ids (ACI, PNI) | both, public | `keys.json` | |
| Phone number | both, public | `number.txt` | Supplied by one operator. |
| Captcha token | both, public | `captcha.txt` | Supplied by one operator, from a file. |
| SMS code | both, public | `code.txt` | Supplied by one operator. **See section 4: it is the real authority over the number.** |
| Verification-session id | both, public | `account.json`, the record | **A weakness: section 4.** |
| Account ids (ACI, PNI) | both, public | `account.json` | From the registration response. |
| Sender certificate | both, public | `certificate.b64`; the account's row | Fetched on the authenticated socket. |
| Username hash, proof, encrypted username | — | — | Not built (section 7). |

## 2. The protocol

A stage is one two-party session (worker pair, handshake with the Signal server inside the
engines). Requests travel as `WebSocketRequestMessage`s on the chat socket, as every other
request of the client does. Request text: `TlsMpc/CeremonyRequests.lean`; the flow:
`PublicServiceController.lean` ("The registration ceremony").

**Before.** One node runs `lss-provision ceremony-keys NAME keys.json` (no network). Its operator
puts `keys.json`, `number.txt` and `captcha.txt` into that node's `STATE/ceremony/`.

**Stage `register`** (unauthenticated socket).

1. Each operator input is read by the node that has it and sent to the other over the workers'
   link (both must end with the same bytes; a node given a different value stops). The key file
   crosses the same way, private keys included (section 5).
2. `POST /v1/verification/session` `{"number":…}` → the session's id.
3. If the session asks for a captcha: `PATCH /v1/verification/session/{id}` `{"captcha":…}`.
4. `POST /v1/verification/session/{id}/code` `{"transport":"sms","client":"ceremony"}`.
5. The nodes wait for `code.txt` (one operator writes it when the SMS arrives), sending a
   keepalive every 20 s; then `PUT /v1/verification/session/{id}/code` `{"code":…}`, which must
   answer `verified: true`.
6. Worker operation 80, kernel `ceremony-secrets`. Private inputs of each node (drawn by its own
   worker): a seed (18 bytes), a mask (22), a recovery half (32). Inside the engine:
   `password = base64(seed_A ⊕ seed_B)[0..22]`, `recovery = recovery_A ⊕ recovery_B`. Opened:
   `masked = password ⊕ mask_A ⊕ mask_B`, nothing else. Node A's password share is
   `mask_A ⊕ masked`, node B's is `mask_B`; each node's recovery share is its own half. Each
   node writes its shares to disk before anything further is sent.
7. `POST /v1/registration`. The controllers build the frame in the clear with two slots of zero
   bytes (32 characters at the end of the `authorization: Basic …` header, 44 in
   `"recoveryPassword":"…"`); worker operation 81 retains it, and kernel
   `ceremony-register-ctr` writes base64 of (the last 0–2 bytes of `NUMBER:`, the password) and
   base64 of the recovery password into the slots under the WebSocket mask and encrypts the TLS
   record. The body's other fields are the public material of `keys.json`.
8. The response (`uuid`, `pni`) is revealed. Each node writes `credentials.share`: its XOR share
   of account id (16 bytes; the public id is in party 0's share) followed by the password (22).

**Stage `certificate`** (authenticated socket). The session is given each node's
`credentials.share` exactly as a receive session is (`accountCredentials`,
`signal-upgrade-shared`): the upgrade succeeds only if the shares combine to the password the
server stored. Then `GET /v1/certificate/delivery?includeE164=false` (the sender certificate) and
`PUT /v2/keys?identity=aci` (the one-time prekeys).

**Stage `store`** (with database nodes). The existing session that creates the account's row
from credentials in two shares: identity key, account id, password and certificate are sealed in
the engines under a key dealt to the database nodes by both parties (operations 53 and 54), and
written under the reserved id 2^128 − 2. Nothing new. After it, send and receive sessions load
the account from the database nodes and need no share file.

Response bodies of these requests are revealed to both controllers (a verification session, the
account's ids, our own certificate). This is a new switch in the reveal policy, `openBody`, set
only by the ceremony stages (NEEDS_REVIEW.md section 3c).

## 3. Operator experience

On BOTH nodes, with the same NAME (it names the sessions):

    public_service_controller ceremony NODE_CONFIG.json NAME register
    public_service_controller ceremony NODE_CONFIG.json NAME certificate
    public_service_controller ceremony NODE_CONFIG.json NAME store        # with database nodes

`NODE_CONFIG.json` is the node daemon's configuration (`node_daemon/README.md`). A stage starts
when both nodes have started it. Files, all in `STATE/ceremony/` of each node:

| File | Who writes it | Content |
|---|---|---|
| `number.txt`, `captcha.txt`, `keys.json` | one operator, before `register` | The captcha token is longer than a terminal's line limit: it is read from this file, never from a prompt. A leading `signalcaptcha://` is dropped. |
| `code.txt` | one operator, when the SMS arrives | The session waits up to 30 minutes. |
| `password.share`, `recovery.share`, `credentials.share` | `register` | This node's shares. **Secret from the other node.** |
| `account.json`, `certificate.b64` | `register`, `certificate` | Public. |
| `record.jsonl` | every stage | The record, below. |
| `register.log` … | every stage | The controller's and worker's diagnostics. |

A node that was not given an input gets it from the other and writes the same file, so both
directories end up alike except for the shares.

**The record** (`SIGNAL_RECORD`, the mechanism of every session): on each node, every byte it
sent in the clear (each public request in full), every server byte revealed to it (each
response in full, bodies included), the server's certificate chain, and for the registration
request the frame as the controllers know it — with the two private slots still zero — plus the
slots' offsets and the mask. The password and the recovery password cannot appear: no controller
ever holds them. The record does contain the captcha token, the SMS code and the session id.

## 4. Who learns what, and what one node can do alone

**Both nodes see:** the number, captcha token, SMS code, verification-session id, every key of
`keys.json` (private keys included), the account ids, the certificate, every response.
**The server sees** what it sees of any registration, password included (it stores a hash).
**Neither node sees** the password or the recovery password.

**The password is hidden from a malicious node** (default mode: malicious, statistical 128):
- It is uniform if either seed is: both seeds are private inputs of the same kernel run, so
  neither depends on the other.
- `masked` is the password XOR the other node's uniform private mask: independent of the password.
- The registration plaintext is never an output of `ceremony-register-ctr`; its outputs are the
  record's header and ciphertext under the TLS traffic key, which no node holds
  (`CeremonyKernel.ceremonyRegisterCtr`). Operation 81 is accepted once per session, and, like
  every operation, only for a frame both workers were handed identically.
- A node cannot make the request carry another password than the one shared: both come from the
  same authenticated wires.
- The stage `certificate` then checks the shares against the server: a node that stored a wrong
  share makes the upgrade fail (401), it does not learn anything.

In semi-honest mode the same holds against a node that follows the protocol.

**A malicious node can:** stop the ceremony at any point (after step 7 the account exists with a
password nobody knows; both shares are already on disk, so the honest flow can resume at
`certificate`; if a share is withheld, the account can only be re-registered with a new SMS);
substitute keys it knows if it is the node that generates them (both nodes hold the keys anyway);
and what follows.

**What a single node holds, and what it can do with it:**

- **It cannot authenticate to the server.** Without the password: no authenticated socket, so no
  fetching of the account's incoming messages, no change of account attributes, no prekey
  upload, no device linking, no new sender certificate, no username, no deletion.
- **It holds the identity private key in the clear.** Consequences the earlier split (identity
  key shared) excluded:
  - It can open the sealed-sender layer of any envelope addressed to the account that it gets
    hold of — the nodes never see envelopes in the clear in a session, but a node colluding with
    the Signal server (or with whoever can read the server's queue) can read **who signs up**:
    the contact list, the one thing the design protects.
  - It can sign prekeys, and with the current sender certificate (valid until it expires) it
    can send sealed-sender messages as the account to anyone whose access key it knows.
  - **Owner's decision** (section 8): accept; or erase the identity private key on both nodes
    after `store` (it then exists only in the sealed row and the engines; protects against a
    node compromised later, not one that kept a copy); or generate it jointly after all.
- **The SMS code and the verification session are the real authority over the number, and both
  nodes see them.** `POST /v1/registration` needs only a verified session's id and any password
  (`PhoneVerificationTokenManager.verifyBySessionId`: the session is looked up, not consumed).
  So a node can register the number by itself, with a password of its own, as soon as the
  session is verified (step 5) and for as long as the server keeps the session — before the
  joint request or after it. With the keys in the clear that is the whole account. The honest
  node notices (its next authenticated upgrade is answered 401), but the account is gone.
  Likewise whoever holds the SIM can always register again.
  - **What would close it** (not built): keep the session id inside the engines. The response to
    step 2 is collected unrevealed (as a prekey response is), a kernel takes the id out of it,
    and the later paths and the registration body get it through slots (as the password does).
    The SMS code is then useless without both nodes. Cost: one small parsing kernel, three more
    slotted requests. And Signal's registration lock (a PIN held in shares) against the SIM.
- **Each share file is a secret of its node.** Whoever gets both `credentials.share` files has
  the password.

## 5. Links

The operator inputs and the key file cross the workers' link (operation 39, `exchange`). On one
machine that is a local socket. In a deployment it must be the authenticated, encrypted link
between the nodes (WireGuard, PRODUCT_TODO.md section 9): the key file carries private keys.

| | |
|---|---|
| `ceremony-secrets` | 1,152 input bits; opens `masked` (22 bytes). `password`, `recovery` private. |
| `ceremony-register-ctr SIZE PAYLOAD AUTH TAIL RECOVERY` | As `bundle-fetch-ctr`: frame size, payload start, the credential slot's offset, how many public bytes of `NUMBER:` precede the password in it (0–2), the recovery slot's offset. Opens the encrypted record. One shape per run: it depends on the lengths of the number, the session id and the key ids. |
| Worker operations | 80 `ceremonySecrets`, 81 `ceremonyRegister` (`tls_worker_v3.cpp`, `service_kernels.h`, `TlsMpc/TlsWorker.lean`). |
| Emitter | `ceremony_kernel_emitter` (`EmitCeremonyKernel.lean`), an executable of its own so that `flat_kernel_emitter` and the cache of every other circuit are unchanged; `circuit_cache.py` routes `kernel ceremony-…` to it. |
| Lean | `TlsMpc/CeremonyKernels.lean` (definitions, kernels), `TlsMpc/CeremonyRequests.lean` (request text), `TlsMpc/CeremonyProofs.lean` (theorems). |

Strict mode (`CIRCUIT_MANIFEST`): the two kernels are not in a deployment's manifest; the
ceremony runs without one (it is a one-time session before the deployment sends anything).

## 8. Decisions for the owner

1. **The session id and the SMS code are public to both nodes**, so one node can register the
   number alone while the verified session lives (section 4). Accept for a first run, or build
   the private session id first.
2. **The identity private key in the clear on both nodes** lets a node that colludes with the
   Signal server read who signs up. Accept, erase after the ceremony, or generate jointly.
3. **Who holds the SIM**, and whether to set a registration lock.
4. **The recovery password** is shared and kept in two files that nothing reads. Keep it (it
   allows re-registration without SMS, by both nodes together), or register without one.
5. **Password format**: 22 characters of base64 (the slot every kernel is built for). Official
   clients use 24 (base64 of 18 bytes); changing the slot changes `signal-upgrade` and the
   account row's size.
6. **The key tool** is the test tool (`lss-provision`); a deployment needs a small audited
   binary for key generation, as for Kyber decapsulation.
