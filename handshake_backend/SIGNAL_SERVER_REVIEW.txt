Source findings:
* SniMapper.buildSslContext explicitly selects TLSv1.3 and ALPN h2. Its supported
  providers are Netty OPENSSL and JDK. It does not set a cipher-suite list, record
  size, padding policy, ticket count or key-update cadence in this method.
* GrpcConfiguration defaults sslProvider to OPENSSL and idleTimeout to 5minutes;
  production config can override these. h2c can remove TLS from this internal
  listener, so source alone does not establish deployment termination topology.
* OmnibusH2Server installs SniHandler and verifies HTTP2 ALPN. It advertises
  RFC8441 extended CONNECT and routes HTTP2 streams via OmnibusRouter.
* WhisperServerService maps /v1/websocket/ and /v1/websocket/provisioning/ to the
  WebSocket backend and routes other H2 paths to the local gRPC server. It also
  configures separate Jetty/Dropwizard HTTPS and WebSocket endpoints.

* Therefore switching library versions is not merely a Signal crypto update.

  TlsWire.Config ALPN/http1.1 as a validated Signal deployment profile.

TLS record consequences (inferences from the stack, not observed production):
Expect certificate-authenticated TLS1.3 and predominantly protected application
records carrying an HTTP byte stream. H2 SETTINGS/PING/WINDOW_UPDATE/GOAWAY and
WebSocket ping/close are application bytes to TLS, not TLS control records.
No source evidence supports one message per TLS record, fixed record lengths,
or skipping fragmentation/coalescing. Keep generic TLS record limits and
streaming framing. The bounded post-handshake parser consumes ignored tickets
and KeyUpdate across records without revealing lengths or ticket bodies.
Our no-resumption ClientHello does not advertise psk_key_exchange_modes, so a
conforming server should not issue tickets for this profile; still ignore
received NewSessionTicket as required by RFC9846 for non-resuming clients.
Provider versions/config affect key-update/ticket/record behavior, so measure
before choosing cached circuit sizes or claiming WAN costs.
