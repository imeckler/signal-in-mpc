# Private immutable-outbox resume candidate

This path reuses committed Signal ciphertext and its original shared request ID. It does **not** rerun the producer, consume fresh Signal state, or allocate an account request ID. A fresh authenticated TLS connection/HTTP101 is mandatory. TLS traffic keys/sequences are fresh, and each transmitted WebSocket frame gets32 fresh joint private VM mask bits (RFC6455§5.3). The retained immutable archive frame is not mutated.

The supported producer profile is certificate260/plaintext80, capacity1290, one admitted pending outbox per conversation, at most four conversations/pending responses. The remask circuit validates FIN binary0x82, masked canonical16-bit0xfe, outer private BE16 length=inner payload length+8, bounds, original validity, computed account resumability, and zero padding outside the private length. It rejects other WebSocket header forms instead of assuming a fixture invariant. It outputs canonical zero padding. Unmasking the new frame gives exactly the old application payload; original request-ID bytes therefore remain unchanged when the account's authenticated outbox binding is valid. Expected ID is retained separately as OwnedBits and reaches the existing private correlation kernel.

`TlsWebSocketRemask` has kernel-checked Hom/compiler agreement, exact output length, exact bounded length-scan acceptance for arbitrary BE16 lengths, and XOR unmask-preservation endpoints with only foundation axioms. Acceptance semantics beyond these endpoints are verified by1157 exhaustive accepted lengths134..1290 and12 malformed/status/padding cases; a full framing-spec refinement theorem is not claimed. The compiler wrapper takes no caller-provided fresh mask: it calls `sbit.get_random_bit()`32 times. Exact closure: `.deps/tls-outbox-remask-native/v1-candidate-1/remask.manifest`,48,476AND triples/1313VM rounds, statistical128. These are component resource counts, not application throughput.

Actual five-party/t2 native test passed four calls: two valid remasks with fresh VM randomness, account-validity rejection, and noncanonical-padding rejection. Only disposable synthetic final frames were opened. Both sampled masks differed; freshness means independently generated unpredictable masks, not a mathematical guarantee of unequal values. All five exited0, cleanup empty, source/product integrity held. No malformed-MAC test or full-account authorization claim.

Actual integration:

- `ConversationAdmission.pending_outboxes` takes only engine-authorized typed payload, shared expected ID, computed resumability, public capacity and fresh public resume lease. The engine maps that lease to certified head/account slot/outbox ordinal; old volatile store tickets are not restored.
- `PrivateMuxRegistry` gives it a one-shot opaque handle. After authenticated upgrade, opcode27 resumes it: enter pending state, privately remask, register old ID correlation, retain the typed result and complete the host barrier. No producer/cursor/Reserve/Commit call occurs on this resume path. The existing committed Signal state remains idle until correlated completion permits new work.
- `CoordinatedConversation` routes correlated completion to the durable account hook with the mapped fresh lease, skipping the old store's volatile ticket check. Timeout/rejection/uncertainty closes the account path; no rollback or blind local retry.
- The restored catalogue uses version2 and includes public opaque outbox handles. Fresh catalogue version1 is unchanged. `RestoredProviderController.lean` sends admitted outboxes before new inputs, after fresh authenticated HTTP101, and requires a resume in its positive test profile. Opcode27 imports no shares/IDs/plaintext and is unavailable through the legacy dispatch profile.

Completed/absent outboxes must not be admitted as resumable by the actual private account policy. Retrying an authorized attempted/uncertain entry can be an at-least-once service request; this layer does not claim server deduplication or recipient delivery. A correlated authenticated2xx means observed server acceptance only. Immutable outboxes/IDs and committed ratchets must survive response-disposition updates; the account owner controls durable outcome persistence. Its actual current-head/full-schema authorization is still a prerequisite, not supplied by hook presence.

Host sanitizer tests exercise the actual conversation/store/mux-registry orchestration with mocked kernels/certificates: two saved old IDs resume while the new account cursor stays fixed, no producer/state transition runs, reordered responses use fresh leases, and stale handle/correlation failure closes the account. Kernel tests/native remasking are separate from those mocks. The Lean restored controller and actual OwnedBits provider API compile. Positive authorized account→fresh TLS→resumed service-peer interoperability remains pending crypto's real engine; production gate stays closed.
