# Restored account request cursor and durable conversation path

Candidate integration checkpoint; normal restored-account admission remains closed.

`NativeSession` now distinguishes a fresh, nonrecovering request-ID allocator from a restored account cursor. The restored cursor stays same-worker `OwnedBits`; the existing pinned range/increment and validity circuits check it without opening its value. The only declassified value is the explicit admission status. Fresh TLS traffic keys, record sequence numbers and WebSocket nonce are independent and are never restored by this API.

Restored reservations stage at most four IDs. `CoordinatedConversation` stages all store callinputs, then invokes the mandatory account Reserve hook once with public conversation slots, exact staged inputs, current/final private cursor and a public lease. Only after that callback finishes can Session install the cursor successor and evaluate a producer. Actual output binding and one whole-account Commit precede store installation/output retention. A pending cursor blocks producer evaluation, output retention and epoch checkpoint. An uncertain Reserve closes the connection; recovery must honor its higher reserved head and burn the entire range. No rollback/retry method exists.

`NativeConversation` is the actual OwnedBits instantiation of this shared implementation. Its existing constructor remains explicitly nonrecovering. Its restored constructor requires a shared durable account owner; batches reject different owners and duplicate account slots. `MuxProviderCoordinator` accepts a restored cursor only with durable conversations from one account and binds public slot ordering in collective inventory agreement. It does not itself prove archive/quorum provenance: the forthcoming crypto-owned factory must consume the actual current-head/full-account authorization result. A boolean or hook presence is not that authorization. No raw-share/plaintext RPC or default provider was added.

The account owner implements `DurableConversationHooks`: Reserve, actual-output binding, Commit, authenticated response completion and poison/close. Response completion is reached only through the existing authenticated/private-correlation coordinator path; it must retain immutable outbox IDs and cannot rewind ratchets/cursor. It may coalesce outcome persistence into the next account checkpoint, leaving earlier restart uncertain. Existing local burn fences remain a further failclosed guard; recovered fence slots must be bound to the authorized head, never relabeled to resurrect old state.

`check.py` passes ASAN/UBSAN over the actual cursor/conversation/staged-store/mux-registry implementation with mocked kernels and certificate persistence. It exercises a two-conversation group, one Reserve/Commit, reordered completion, stale receipt rejection, and failure **after durable reservation but before cursor install** followed by simulated restart that skips the complete range while retaining earlier outbox IDs. The real OwnedBits provider/coordinator boundary also compiles and links against the pinned cache-candidate runtime.

The restart fixture assumes an authorized burned cursor/current head. It does not resolve an actual incomplete Reserve certificate: the account coordinator currently rejects an unresolved higher reservation, which safely blocks rollback/activation. Continuation needs its authorized resolution policy.

These are host orchestration tests, not quorum-authorized recovery or TLS interoperability evidence. Required next test: crypto's actual account authorization/import/coherence/cleanup token → fresh Session/handshake/WebSocket upgrade → restored durable provider → local protocol-faithful peer, with pending outbox disposition and restart/error controls. Candidate runtime failure/erasure composition and full-account schema must pass before production gate promotion. ## Explicit launcher (positive authorization still pending)

`tls-restored-mux-worker` is a separate link-selected profile (`TLS_ACCOUNT_FACTORY`). Its default `NoAccountRecovery.cpp` returns no resolver. `AccountAdmission.h` is crypto-owned: only `AccountRecoveryEngineV1` can construct the one-shot `AuthorizedRestoredAccount`. The launcher creates Machine plus a bootstrap Worker, collectively checks resolver availability, calls the resolver outside an erased host call, then destroys its closure/bootstrap Worker in a later erased host call before constructing a **new** Session. The resolver owns actual import/helper teardown/VM retirement and returns only after both host barriers. No TLS state exists during import.

After a real fresh handshake/retirement succeeds, the provider factory consumes that capability once; no CLI/RPC can construct it. Abort or any failed handshake/RPC clears an unconsumed capability inside an erased host call. Restored Bits must be value-owned by the capability/account coordinator: `Worker::allocate` returns independent `OwnedBits` vectors, and Worker destruction wipes its own scalar, not an allocation arena. The actual positive restore→new Session test must verify this continuity; a callback that captured bootstrap-stack/Worker references would violate admission and is not permitted.
